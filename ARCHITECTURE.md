# Reiss Family Recipes — Architecture

## Overview
A recipe collection site for Yidi and Nava Reiss. Vanilla HTML/CSS/JS, no build step, no login gate. Hosted on GitHub Pages at https://yidireiss.github.io/recipes/.

## Components

### 1. Static Site (`site/`)
- `index.html` — Single-page app shell. Loads `app.js` with a cache-busting version query.
- `app.js` (~2,100 lines) — All client logic: routing, recipe list, recipe detail, meal planner, shopping list, submit page, manual editor, inbox log.
- `styles.css` (~950 lines) — All styling, mobile-first.

**Data loading:** On boot, fetches `data/recipes/meta.json` and `data/shopping-sections.json` (parallel via `Promise.allSettled`), plus the live meal plan. Full recipe JSONs load on demand via `ensureRecipe()`. Missing `shopping-sections.json` degrades gracefully to flat alphabetical shopping list. All metadata held in memory for instant search/filter.

### 2. Write Bridge (Cloudflare Worker)
- **URL:** https://recipe-bridge.leibreiss.workers.dev
- **Source:** `bridge/worker.js` (local mirror). Deployed source of truth: PRIVATE repo `YidiReiss/recipe-bridge` — Cloudflare Workers Builds auto-deploys every push to `main` (`wrangler.toml`: `keep_vars = true`, `[secrets] required = ["GITHUB_TOKEN"]`). Dashboard-editor deploys are retired (the Monaco editor can't receive automated input). See `bridge/DEPLOYED.md`.
- **Purpose:** Holds the GitHub fine-grained token server-side. The public site POSTs writes to the worker; the worker commits via GitHub API.
- **Endpoints:**
  - `GET /health` — liveness check (returns a `version` marker identifying the deployed build)
  - `GET /read?path=` — fetch file content + SHA from GitHub
  - `POST /save` — raw file write `{path, content, message, encoding}` (PDFs, images, index files)
  - `POST /save-recipe` — recipe write with server-side history `{path, recipe, actor, reasoning, base_sha, action, skip_log}`. The worker fetches the live file, diffs against incoming, appends a history entry, and commits. Returns 409 if `base_sha` doesn't match (optimistic concurrency — prevents lost-update races). Also auto-logs every edit to `data/inbox/index.json` (type `direct-edit`) unless `skip_log` is set — see §2b.
  - `POST /delete` — file deletion
- **Security:** Token never touches the repo or browser. Allowlisted paths only.
- **Deploy record:** `bridge/DEPLOYED.md`

### 2a. Recipe Change History
Each recipe JSON has a `history` array logging all changes. Entries: `{ts, actor, action, changes, reasoning}`.
- **Actions:** `intake` (creation), `edit` (manual/app edit), `estimate` (Sous Chef batch), `re-press` (PDF regeneration)
- **Actor format:** `site-editor (Name)` for app edits (name from localStorage prompt), `sous-chef` for intake checker
- **App UI:** Edit page shows collapsible history section; optional "why did you change this?" input by Save
- **Race protection:** App captures SHA on edit-page load; worker rejects stale saves with 409

### 2b. Recent Submissions Auto-Log
Every `/save-recipe` **edit** is mirrored into `data/inbox/index.json` as a `type: "direct-edit"` entry (index-only, no per-entry file), so no edit path can bypass the Recent submissions log. Skipped: new recipes, `action: "re-press"`, callers passing `skip_log: true` (the intake checker, whose edits are already represented by their submission entry), and saves whose only diff is the `pdf_stale` flag flip. A reasoning-only save still logs. Entries carry `edit_target`, `recipe_id`, the recipe's current title, the actor, and a note (the reasoning, or a changed-field summary). Logging is best-effort (2-attempt SHA retry) and never fails the recipe save; the index is capped at 300 entries, never evicting pending/needs_input.

### 3. Sous Chef Skill (`~/workspace/skills/sous-chef/SKILL.md`)
The intake compiler. Takes any input (link, photo, pasted text, YouTube) and produces standardized recipe JSON + banner photo. Used by the intake checker.

Key rules:
- Ingredient item/prep splitting (buy vs cook)
- Unit normalization (tbsp, tsp, cup, lb, oz)
- Never silently kosherize — flag with `needs_kosher_review`
- Duplicate detection before publishing
- YouTube: include channel name in title
- Edit requests (type: "edit"): apply only requested changes to existing recipe

### 4. Recipe Press Skill (`~/workspace/skills/recipe-press/SKILL.md`)
PDF generator. Takes recipe JSON + banner photo, produces a styled PDF with:
- Hero photo, ingredients sidebar, tips section
- Kosher color theme (meat red / dairy blue / pareve green)
- Leftovers badge
- **Engine:** `intake/make_pdf.py` (~250 lines, Python)

### 5. Intake Checker (cron: `recipe-intake-check`)
- **Schedule:** Every 30 minutes, America/New_York
- **Skips:** Shabbat and Yom Tov (reads quiet-hours calendar)
- **Pipeline:**
  1. Check bridge health
  2. Fetch inbox index, find `pending` entries
  3. For each: duplicate check → mark working → analyze via Sous Chef → extract recipe → photo chain → Press PDF → upload via bridge → mark done
  3a. **Batch inventory + auto-split (photo entries, step c0):** before extraction, inventory ALL of an entry's photos as one set (order doesn't matter) using start signals (title header, fresh ingredient list) and continuation signals ("Continued" header/column, "Page X of Y" footers, continuing step numbers, printout footer title). A note stating the grouping overrides detection. One recipe → normal pipeline. 2+ recipes with unambiguous boundaries → auto-split into one child inbox entry per recipe (photo subset per recipe; a photo may be shared by two children); the parent is marked done with the child ids in its note; children process as ordinary pendings (10/run cap counts the parent as one). Ambiguous grouping or an orphan fragment (a continuation whose start page isn't in the batch) → never guess: confident recipes still split off; the affected recipe becomes a child marked `needs_input` with its photo(s) sent to Yidi. When the last split child resolves, the checker sends ONE batch summary. Test mode: inventory + split plan written to the /tmp result file only, no children created.
  4. Process edit requests (type: "edit") via Sous Chef section 7
  5. Re-press queue: regenerate PDFs for recipes with `pdf_stale: true`
  6. Report only on failures (3+), needs_input, duplicates, or bridge issues

## Data Schema

### Recipe JSON (`data/recipes/<id>.json`)
```json
{
  "id": "slug-id",
  "title": "Recipe Title",
  "kosher_status": "meat|dairy|pareve",
  "kosher_for_passover": false,
  "needs_kosher_review": false,
  "kosher_review_notes": "",
  "categories": [],
  "prep_minutes": 0,
  "cook_minutes": 0,
  "servings": "",
  "ingredients": [{"section": "", "items": [{"qty": "", "unit": "", "item": "", "prep": ""}]}],
  "instructions": [],
  "tips": [{"title": "", "text": ""}],
  "tags": [],
  "notes": "",
  "source": "",
  "pairings": [{"recipe_id": "", "note": ""}],
  "banner_image": "assets/images/<id>.jpg",
  "photo_generated": false,
  "pdf": "pdfs/<id>.pdf",
  "pdf_stale": false,
  "leftover_friendly": false,
  "needs_side": false,
  "leftover_note": ""
}
```

### Metadata Index (`data/recipes/meta.json`)
Lightweight array of recipe metadata for list/search/filter/sort. Each entry mirrors the recipe's card-relevant fields (id, title, banner_image, kosher_status, categories, tags, prep_minutes, cook_minutes, servings, etc.) plus a `search_text` field and, since 2026-10-31, a derived `needs_side` copy of the recipe's planner flag (the recipe JSON is the source of truth; meta patches must preserve it, like `variants`). Updated on every site save (saveRecipe/saveNewRecipe) and by the intake checker when adding recipes. Since 2026-11-04 (Worker `git-v6`), the Worker is the single writer for cards: it rebuilds the card on every `/save-recipe` (including re-press) and upserts it into `meta.json` (fresh read, SHA guard, one 409 retry; a card-write failure is reported as `meta_write_failed` and never fails the recipe save); the site editor consumes the returned card instead of writing `meta.json` directly (the delete-flow cleanup still writes `meta.json` directly from the browser). Cards now also carry `ingredients_text` (ingredient names only) alongside `search_text`.

**2026-10-15 lost-update fix:** GitHub's Contents API returns `Cache-Control: max-age=60`. Rapid-fire saves (<60s apart) caused each save's `ghGet('data/recipes/meta.json')` to return a stale cached copy, silently reverting the previous save's entry (confirmed via git history: two reverts 38s and 36s after the correct writes). Fix: `ghGet` appends `&t=Date.now()` and uses `cache: 'no-store'` on all reads; meta.json updates retry once on failure with a user-visible toast ("please click Save again") instead of silent `console.warn`.

**2026-10-21 checker-side safeguard:** The 2026-10-15 fix hardened only the app's writes. The intake checker still rewrote `meta.json` (and `index.json`) from copies fetched via `raw.githubusercontent.com` (Fastly CDN, minutes-stale), so the Oct 20 22:42 run erased the 3 salmon cards added at 22:12 (5 cards lost in total, incl. two older recipes). Standing rules now in the checker cron body (step g) and Sous Chef skill §5: before writing either file, fetch its current content via the bridge `/read` (server-side API, fresh), merge additively by id, skip if unchanged, and verify after writing (entry present, count not shrunk; re-apply up to 3×). The checker also runs a per-run consistency self-heal (step 5a): it compares the `index.json` and `meta.json` id sets via the bridge, rebuilds missing cards from the recipe JSONs, drops meta entries whose recipe file is gone, and reports any repair to Yidi.

### Inbox Entry (`data/inbox/<id>.json`)
```json
{
  "id": "inbox-xxx",
  "type": "submission|edit",
  "edit_target": "<recipe-id>",
  "url": "",
  "image": "data/inbox/<id>.jpg",
  "images": ["data/inbox/<id>.jpg", "data/inbox/<id>-p2.jpg"],
  "note": "",
  "text": "",
  "status": "pending|working|done|failed|duplicate|needs_input",
  "created_at": "ISO timestamp",
  "recipe_id": "<created recipe id>",
  "duplicate_of": "<existing recipe id>",
  "fail_reason": "",
  "needs": []
}
```

**Multi-photo submissions (2026-10-21):** a submission may carry up to 6 photos. `image` always holds the first photo's path (older consumers keep working); `images` holds every photo path in submission order (`null` when there are none). Additional photos are stored as `data/inbox/<id>-p2.<ext>`, `-p3`, … and keep their real extension when the browser couldn't resize them (png/heic/webp). The intake checker reads ALL photos in order as pages of one recipe (self-correcting order from page/step cues), applies the unified banner rule (clearest finished-dish photo wins; if every photo is a text page, the banner falls through to the link/PDF/AI chain), flags multi-recipe photo dumps (`needs: ["recipe_selection"]`) and unreadable photos (`needs: ["clearer_photo"]`) as `needs_input` instead of guessing, and re-runs duplicate detection after extraction. The Submit page holds photos in `window._submitPhotos`, uploads them sequentially (parallel GitHub Contents writes would 409), disables Submit with a per-photo progress status, and its localStorage draft sheds photos — never the text fields — when the storage quota runs out. Photo resize cap: 2400px longest edge, JPEG quality 0.85 (raised from 1600px on 2026-10-21; the same cap applies to edit-page banner uploads and the checker's banner pipeline).

### Inbox Index (`data/inbox/index.json`)
Array of entry summaries — lightweight for the log display. Submissions carry `{id, status, type, created_at, ...}`; worker-generated edit log entries carry `{id, status: 'done', type: 'direct-edit', edit_target, recipe_id, title, actor, note, created_at}`.

## Auto-Logging Edits (2026-10-19)
`/save-recipe` is the single choke point every recipe edit passes through (site UI, Sous Chef cron, ad-hoc API calls), so edit logging lives there: after a successful recipe commit, the worker appends a `direct-edit` summary to `data/inbox/index.json` — index-only, no separate per-entry file (the UI renders direct-edit entries entirely from the index; the full diff already lives in the recipe's `history[]`). Guard logic: log only when the recipe already existed, `action !== 're-press'`, the caller didn't pass `skip_log: true` (the checker's edit requests opt out — they're already represented by their inbox entry), and there's a meaningful edit — computed by filtering `pdf_stale` out of the server diff (`realChanges`), so a flag-only flip doesn't log but a reasoning-only save does. The note is the caller's reasoning (truncated at 200 chars) or a "Changed <fields>" summary. Logging runs in a try/catch (`appendInboxLog` helper, 2-attempt SHA retry with 150ms backoff on 409/422) and can never fail the recipe save. The index is capped at the last 300 entries, never evicting `pending`/`needs_input` entries.

## Shopping List Sync Design (2026-10-13)
Checkmarks are stored as `{key, session, at, qty, unit}` objects in `week.haveGenerated`, where `session` is a per-tab ID and `qty`/`unit` capture the line quantity at tap time.

**Key stability:** Item keys are `base|rawUnit` (non-pluralized). The display label may pluralize (`cup`→`cups`) but the key never changes with quantity.

**Sync flow (offline-first):**
1. Tap → mark stored in memory + localStorage immediately; `_shopDirty = true`; 2s debounce.
2. `syncShop()`: pushes via `saveMealPlan()` (below), which re-reads the fresh server copy and merges before writing — the push is the union, never a stale overwrite. Server can never wipe local marks.
3. `pollShopServer()`: every 15s, fetches via bridge `/read` (live GitHub API, bypasses Pages rebuild lag) and merges via `mergeMealPlan()`.
4. `online` event: if dirty, syncs immediately when connectivity returns.
5. `boot()` / `refreshMealPlan()`: use `fetchLiveMealPlan()` (bridge `/read` first, Pages fallback) and `mergeMealPlan()` — never blind-overwrite.
6. **Mid-save tap survival (`app.js?v=20261101j`):** `attemptSaveMealPlan()` captures `_shopDirtyGen` (incremented in `markShopDirty()`) at the merge point and, after `ghPut` settles, assigns `mealPlan = mergeMealPlan(merged, mealPlan)` and clears `_shopDirty` only if `_shopDirtyGen === savedGen` (otherwise keeping `_shopDirty = true` and calling `syncShopSoon()`), so a tap landing during `await ghPut` is never overwritten or left unsynced.

**Meal-plan save unification (2026-10-22, `app.js?v=20261022a` — Smart Meal Planning v1, Commit 1):** Every write to `data/meal-plan.json` now goes through one serialized writer, `saveMealPlan(mutator, message)`. Saves queue on a module-level promise chain (`.then(run, run)` so a failure can't poison the queue); each attempt re-reads the fresh plan via `bridgeReadMealPlan()` (bridge `/read` only — never the Pages CDN; a failed read fails the save), merges with `mergeMealPlan(fresh, local)`, applies the caller's mutator last, and writes via the single remaining `ghPut('data/meal-plan.json', …)` call site. Retries: at most 3 attempts, 400ms backoff, only on failure; no verify-read after a successful save. `mergeMealPlan` rules: for each shared week, **fresh wins** (`days`, `shoppingDay`, `dismissedWarnings`); only the 4 shopping keys (`haveGenerated`, `manualItems`, `optionalPromoted`, `conflictAcked`) merge in from local via `mergeWeekState()`; local-only weeks are kept untouched; top-level `recipePrefs` merge per recipe id (latest `updatedAt` wins, ties to fresh), `yieldLog` unions by entry id (latest 200 by date/id), `framework` goes to the latest `updatedAt`. `persistWeek()` captures a shallow copy of the caller's edited week and its mutator applies that copy, then `mergeWeekState(next, prevMergedWeek)` pulls the freshly merged shopping keys back in — so a planner save can never wipe shopping marks another device just made on the same week (Argon diff-review catch, 2026-10-22). An `_savePlanInFlight` counter makes `maybeRefreshPlan`/`refreshMealPlan`/`pollShopServer` skip while a save is in flight, so a poll can't flash pre-commit state. `loadShopLocal()` also recovers through `mergeMealPlan()`, so offline top-level state (prefs/yieldLog/framework) restores like shopping marks. The planner previously wrote the whole plan blind (`persistWeek` overwrote via `ghPut`); that path is gone. Verified by `smart-planning/commit1-merge-test.cjs` — 47 assertions against the real extracted functions (stale-tab days never win, shopping/tombstone merges, LWW, yield cap, serialization, retry semantics, cross-device marks scenario, boot recovery). **Bundled fix:** `weekStripHTML()` (Shopping page week strip) now reads slots via `normalizeSlot(...).dishes` and joins all dish titles — it previously read legacy `slot.recipe`/`slot.custom`, so every meal rendered as "—".

**Smart planning engine (2026-10-22, `app.js?v=20261022d`, `styles.css?v=20261022a` — Smart Meal Planning v1, Commit 2 + rule-5 v3 soft-target fill; spec: `smart-planning/SPEC.md`):** A runtime classifier + one-tap week generator on top of Commit 1's writer. `inferPlanningMeta(meta)` is pure/deterministic (categories + title + `search_text` + times): a main-slot eligibility gate (categories include `main`, or a `recipePrefs` slotClass override), `slotClass` in priority order (ground-beef → beef-roast → chicken → fish → pasta → veg → other; protein regexes carry broth/stock negative lookaheads; chulent classifies by its actual protein, effort `shabbat`, fit `lunch`), `effort` (time bands by total minutes with per-class caps and a `sunday` tier between weeknight and shabbat — standard classes: weeknight ≤60, sunday ≤75, beyond → shabbat; ground beef: weeknight ≤75, sunday ≤90; `shabbat` also via explicit tag / beef-roast class / meat with no times; `special` is manual-only and never auto-drafted; Sunday's generator pass and swaps draw {weeknight, sunday} on day 0 only, Mon–Wed draw {weeknight}), and `shabbatFit` (friday/lunch/both). `effectivePlanningMeta(id)` layers `recipePrefs` overrides (rating favorite/fine/skip, effort, slotClass — slotClass also lifts the gate) and passes the meta card's `variants` through. `leftoverServings(dish, meta)` is the single yield source of truth: learned `yieldLog` values are already post-dinner leftovers and are used directly (median of last 3 exact recipe+scale+variant matches; cross-scale inference `(2 + logged) × scale − 2` floored at 0); the fallback is `max(0, floor(servingsLow × scale − 2))` with a leftover-friendly bump to 1. `draftWeek(weekKey, chips)` fills in order: eat-out chips reconcile two-way (auto-mark note exactly `Eat out`; manual skips never touched; Thu exempt; Saturday governs lunch only — see 2026-10-31 entry below) → Thu dinner standing Pizza (locked) → Fri dinner + Sat lunch Shabbat mains (hosting chips add a natural-size bonus only — the generator NEVER writes `dish.scale`; both mains ≥90 min puts a Thursday `cookDate` on one) → Shabbat-leftovers night Mon (fallback Tue, never Sun) sourced from the previous week's Shabbat mains with proven yield ≥2, deducting 2 from the carry-in pool via `week.carryInDeductions` → Sun–Wed framework POOL fill (rule-5 v3, Yidi 2026-10-22: soft weekly targets beef 1 / pasta 2 / chicken 2 / fish-veg 1 as score penalties, not hard caps — every candidate competes on its normal score minus 25 per pick its bucket already has this week, minus 60 more per pick beyond target, minus 15 if its bucket matches the previous night's; bucket counts start from dishes already standing in Sun–Wed slots after unprotected slots are cleared, counting only main-eligible or leftovers dishes, variant-aware — so the rule-4 leftovers dish counts toward its own class's target and Q4 "leftovers replace their own kind" falls out of the counting; a night stays empty only when no framework class has any candidate) → `recomputeWeekLunches()`. Scoring: favorite +30 / fine +18 / unrated +12, never-cooked +6 (bonus capped at the week's first untried pick), recency to −40 (favorites exempt after 2 wks), use-up +8/hit (cap +24), +10 leftover-selection bonus; every drafted dish carries a plain-words `reason`. `recomputeWeekLunches(weekKey)` is a pure helper over stored weeks: leftover buckets stay usable 7 days from cook day (incl. the Shabbat carry-in pool from the previous week's Fri dinner/Sat lunch mains, cook offsets −2/−1), FIFO allocation, spacing (a source never appears on 3 consecutive days, counting its own dinner; bridge cases included), no Sunday/Saturday auto-placements, needs Mon–Thu 2 / Fri 1, partial coverage places the dish with `dish.coverage` + a `week.lunchWarnings` entry; locked/manual leftover lunches charge their buckets, and manual leftovers dinners of a pool source charge the pool (recorded deduction, else 2) so deletes refund. Swap (`swapCandidates`/`applySwap`) cycles the slot through its top-5 same-class candidates (a variant dish's class is its version's class, so the variant follows the slot; fish and veg form one framework bucket, so a fish dish also swaps against veg candidates and vice versa); Swap is hidden on leftovers dishes. Shopping: `buildShoppingList()` collects `{id, scale, variant}` per dish — quantities multiply by the manual scale, and a variant dish buys shared + only its version's tagged ingredients. **Draft snapshots — the learning loop (2026-10-22, `app.js?v=20261022e`, commit `b5fd5ca`):** Yidi's expectation is that the planner's stated rules and the family's actual behavior will diverge, so for roughly the first two months a weekly review diffs what Draft Week proposed against what was actually eaten and proposes tuning changes (nothing auto-changes). The mechanism: `draftWeek` records a snapshot into the top-level `mealPlan.draftSnapshots[weekKey]` — `{ draftedAt, firstDraftedAt, draftCount, chips, days, firstDays, lunchWarnings }` — where `days` is the latest draft and `firstDays`/`firstDraftedAt` preserve the week's FIRST draft across re-drafts. Snapshots live outside the week records because `mergeWeekState` only merges shopping keys, so week-record fields are at risk on the stale-tab `persistWeek` path. `mergeMealPlan` unions snapshots per weekKey via `mergeDraftSnap` (latest `draftedAt` is the base; `firstDays`/`firstDraftedAt` survive from the earliest draft; `draftCount` = max) and prunes to the 12 most recent weekKeys, so stale tabs can't resurrect pruned weeks. `persistPlannedWeek` captures the snapshot synchronously and re-applies it inside its save mutator via `mergeDraftSnap` — a queued save that settles first can replace the in-memory plan with a copy computed before the snapshot existed, and without the re-apply it would wipe the snapshot in memory (Argon race guard; the merge is idempotent, so swap/lock saves through the same path are no-ops). The weekly diff is mechanical from dish fields: kept = same recipe still `drafted:true`, swapped = different recipe still `drafted:true`, manually replaced/added = `drafted` falsy, cleared/skipped = snapshot dish gone. Verified by `commit2-test.cjs` §27 (suite now 138 assertions; 228 total across the three suites) and live: a test draft of the Nov 1 week wrote `draftSnapshots["2026-11-01"]` (draftCount 1, `days` + `firstDays` present) to production `data/meal-plan.json`, and the week was restored empty afterward (the snapshot itself remains by design).

**Quantity splits:** If a marked qty is less than the current line total (e.g. checked "1 cup honey", now need 3 cups), the line renders as two: checked portion + unchecked remainder. Tapping the checked portion unchecks all; tapping the remainder checks the full qty.

**Optional ingredients:** Ingredients with `optional: true` appear in a collapsed "Optional" section on the shopping list (never in "To buy" by default). Two buttons per item: "+" promotes to To Buy (tracked in `week.optionalPromoted`, merged on sync), "✓" marks Already Have directly. Tapping "○" on a promoted item in To Buy sends it back to Optional. If an item is required in any planned recipe, the aggregated line is required (optional only wins when ALL occurrences are optional).

**Pantry staples filter (2026-10-21):** The Shopping page head carries a "Hide pantry staples" checkbox (per-device localStorage `recipe-hide-staples`, default off). `PANTRY_STAPLES` is a curated set of base names; `isPantryStaple()` exact-matches a line's groupKey base name after hyphen/apostrophe normalization. `splitShopItems()` partitions aggregated lines into To Buy / Already Have / Optional (quantity-aware) and is shared by the render and Copy list; `partitionStaples()` then moves staple To Buy lines into a collapsed "Pantry staples (N)" section (promoted staples exempt; manual items and undecided Optional lines never filtered). `renderShopWrap()` re-renders `#shop-wrap` while preserving which `<details>` sections are open, so taps and the 15s sync don't collapse them.

**Pantry staples update (2026-11-01, `app.js?v=20261101h`, commit `188e07a`, Pages #1582):** the set gained `'honey'`, `'coarse salt'`, and `'himalayan salt'` (Yidi, Nov 1, 2026); `isPantryStaple` now strips a trailing parenthetical from the normalized base (Option A) before the set lookup, so parenthetical variants such as `honey (add to sauce)` hide/merge with the base staple; `COUNT_TO_TSP` no longer converts garlic cloves to teaspoons (onion/lemon conversions stay), so clove-count garlic renders as cloves. **Conflict detection:** Same item marked by 2+ distinct sessions renders red with "⚠️ Both grabbed this" warning.

**Tombstone merges (2026-10-20, `app.js?v=20261020b`):** The original union-only merges could never propagate a removal: deleting a manual item, unchecking a mark, or un-promoting an optional was undone within seconds when the pre-change server copy merged back. All three state types are now timestamp/tombstone merges (`mergeHaveMarks`, `mergeManualItems`, `mergePromoted`, used by both `pollShopServer()` and `mergeWeekState()`):
- **Have-marks:** unchecking sets `removed: true` + a fresh `at` on the mark instead of deleting it. Merges keep one entry per (key, session) — the newest `at` wins. Renders use `activeHaveMarks()` (deduped, tombstones dropped). Two sessions checking the same key still union, so conflict detection is unchanged.
- **Manual items:** deleting sets `deleted: true` + `updatedAt`/`updatedBy` instead of removing the object. Every mutation (add/check/uncheck/delete) stamps `updatedAt`. Merges: a tombstone always beats a live copy; otherwise the newest `updatedAt` decides the have state and `haveSessions` union when the result is "have".
- **Optional promotions:** entries are `{key, promotedAt, removedAt}` objects (legacy string entries read as `{key, promotedAt: 0, removedAt: null}`). Active = `promotedAt` set and later than `removedAt`. Un-promoting stamps `removedAt`; merges carry the latest of each timestamp forward.
Verified by `qa/shop-sync-test.cjs` — 20 stateful scenarios (delete/uncheck/un-promote survival, concurrent two-device checks, legacy shapes) run against the real functions extracted from app.js.
